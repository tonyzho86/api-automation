# 实战练习

README 让你"看懂",这里让你"会写"。**从易到难,每一题都能立刻验证。**

做完一题就跑一次 `run-tests.cmd`,看绿灯。

## Level 1 · 照葫芦画瓢(熟悉套路)

### 1.1 给商品详情补一条用例

`tests/test_02_product.py` 里已经有 `test_product_detail`,照着写一条
`test_product_detail_price_matches_list`,断言:详情页拿到的 `price`,
和它在列表里出现的 `price` 一致。

> 考点:**接口之间的数据一致性** —— 列表和详情对同一个商品,不该给出两个价。

### 1.2 给购物车补一条边界用例

往购物车里加 **0 件**商品,写用例断言"应该怎么处理"。

- 先想想:数量 0,到底是合法(等于不加)还是非法(应该 400)?
- 然后**先断言你期望的正确行为**,再跑,看它是不是红的,红的就去 `BUGS.md` 找线索。

> 考点:**测边界时先想清楚"期望",再写断言。** 期望说不清,用例就没意义。

## Level 2 · 动手改造(理解分层)

### 2.1 加一个商品接口的上限校验用例

给 `GET /api/products` 传一个巨大的 `size`(比如 `size=100000`),
断言返回条数不超过 `total`。

> 考点:接口**即使不报错**,也可能给出不该给的东西。边界不止"非法值",还有"极端合法值"。

### 2.2 用数据驱动重写 Level 1.2

把"购物车数量边界"做成参数化:`0`、`-1`、`-999`、`999999`,数据放 `data/` 下新建的
`cart_cases.yaml`,用例只写一遍。

> 考点:**规格变了只改数据,不改代码** —— 这是数据驱动的全部意义。

## Level 3 · 独立设计(测试思维)

### 3.1 给"下单"设计一整套用例

不看现有用例,自己列一个清单,覆盖:

- **正常**:单商品 / 多商品 / 用券 / 不用券
- **边界**:金额刚好等于券门槛(100)/ 差一分(99.99)/ 超出库存
- **异常**:空订单 / 不存在的商品 / 数量为 0 / 数量为负
- **权限**:未登录 / 用别人的 token
- **幂等**:同一下单请求重复提交

先写在纸上(或注释里),再落成代码。**能列全,才是真的会设计用例。**

### 3.2 找接口之间的"组合 bug"

现有用例都是**单接口**的。真 bug 常常藏在**接口之间**:

- 加购物车 → 下订单 → 购物车该被清空吗?现在清了吗?
- 下单后库存减了吗?库存不够还能下单吗?
- 取消订单 → 库存加回来了吗?

挑一条链,写**端到端**用例,看看会挖出什么。

> 考点:**接口测试的价值不只在单个接口对错,更在于业务流程的一致性。**
> 这里很可能会挖出第 7、第 8 个缺陷 —— 它们没写在 `BUGS.md` 里,是你的发现。

## Level 4 · 上强度(贴近真实工作)

### 4.1 加一份"接口契约"校验

给每个接口定义 JSON Schema,做成**一条用例校验所有响应结构**。
`framework/core/asserts.py` 里的 `assert_schema` 已经准备好了。

> 考点:接口回归时,字段**类型/必填**变了(比如 `id` 从 int 变 string)是最隐蔽的坑之一。

### 4.2 给框架加"响应时间"断言

`ApiClient` 已经把每次请求耗时挂在了 `resp.elapsed_ms` 上。写个用例,
断言关键接口(比如登录、商品列表)响应 < 500ms。

> 考点:接口测试不止功能,还有**性能基线**。

### 4.3 接进 CI

参考 `D:\projects\web-automation\.github\workflows\e2e.yml`,给这个项目写一份
GitHub Actions 工作流:起 SUT → 跑用例 → 上传 `report.html`。

## 卡住了怎么办

- 断言红了但看不出原因 → 看用例输出里那三行:**状态码 / 实际值 / 响应体**,答案都在里面
- 不确定接口"应该"什么样 → <http://127.0.0.1:18800/docs> 看文档,或看 `sut/app.py` 的实现
- 想验证某个请求到底发了什么 → 每次请求都有日志,终端里看 `GET /api/... -> 200  12.3ms`

# 设计说明

这份文档记录工程里的关键设计决策:**为什么这么做、放弃了什么、什么情况下该换方案**。
面试时被追问"你为什么这样设计",答案基本都在这里。

---

## 1. 目标与约束

**目标**:一套可以复用到真实项目的接口测试工程,而不是一次性脚本。

**约束**:

- 被测系统不可控(真实项目里服务端不会为你改代码)
- 接口会变(路径、参数、字段名)
- 用例会膨胀(从 30 条到 300 条)

这三条约束决定了架构:**变化点必须被隔离**。

---

## 2. 分层与理由

```
用例层 tests/          业务逻辑与断言
   ↓
接口层 framework/api/  接口定义(URL、参数、返回)
   ↓
核心层 framework/core/ HTTP 传输与断言工具
   ↓
配置层 framework/config/ 环境与凭据
```

### 为什么要单独一层"接口层"?

**没有接口层时**,用例长这样:

```python
resp = requests.get(f"{BASE_URL}/api/products", params={"page": 1, "size": 5})
```

**有接口层时**:

```python
resp = api.product.list(page=1, size=5)
```

差别不在"少写几个字符",而在于:

- URL、参数名、请求头只在**一处**定义。接口从 `/api/products` 升到 `/v2/products`,改 1 个文件,而不是改 80 个用例。
- 用例读起来是业务语言,新人不需要知道接口细节也能看懂。
- 接口层是**唯一**允许出现"HTTP 细节"的地方,职责边界清晰。

**取舍**:多了一层间接,初期写起来更啰嗦。超过 20 条用例后收益才明显。

### 为什么核心层要自己封装 HTTP 客户端?

直接用 `requests` 完全可以,但会丢掉三样东西:

1. **统一的 base_url 与超时** —— 否则每条用例都要拼地址
2. **请求日志** —— 用例失败时,"到底发了什么请求、返回了什么状态码"是第一现场
3. **耗时采集** —— 挂在 `resp.elapsed_ms` 上,后续加性能断言不用改传输层

日志的实际价值被低估。真实项目里排查一条偶发失败,80% 的时间花在还原请求现场。

### 为什么断言也要封装?

裸写 `assert resp.status_code == 200`,失败时你只得到一行 `AssertionError`,还得回去翻日志。

封装后的失败信息:

```
状态码不符  期望=400  实际=500
请求        GET http://127.0.0.1:18800/api/products?page=1&size=0
响应体      Internal Server Error
```

**排查时间从几分钟压到几秒。** 这是测试框架里投入产出比最高的部分。

## 3. 测试数据的隔离策略

**问题**:用例之间会互相污染。前一条用例加了购物车,后一条用例看到脏数据。

**方案**:被测服务提供 `POST /api/_test/reset`,`conftest.py` 里用 `autouse` fixture 在每条用例前重置。

```python
@pytest.fixture(autouse=True)
def _reset_sut(client):
    client.post("/api/_test/reset")
    yield
```

**取舍与边界**:

- 这是**测试专用接口**,真实项目通常没有。替代做法是每条用例自己造数据并用唯一标识隔离,或用数据库事务回滚。
- 重置接口降低了用例的独立性(用例必须知道"环境是可重置的"),但换来了可重复执行。
- 更正规的做法是**每类资源一个 fixture 负责创建与清理**,而不是全局重置。本工程规模小,选择简单方案。

**面试可以这么讲**:"隔离方案取决于被测系统给不给测试留口子。能重置就重置,不能重置就用唯一数据 + 定向清理。"

## 4. 数据驱动为什么用 YAML?

```yaml
- name: 单商品_满100_用券
  items: [{product_id: 5, quantity: 1}]
  coupon_code: SAVE20
  expected_total: 129.0
  expected_discount: 20.0
  expected_payable: 109.0
```

对比另一种做法(把数据写在 `@pytest.mark.parametrize` 里):

| | YAML | 代码内参数化 |
|---|---|---|
| 非开发人员可维护 | ✅ | ❌ |
| 加场景不改代码 | ✅ | ❌ |
| 类型安全 / IDE 提示 | ❌ | ✅ |
| 复杂逻辑表达 | ❌ | ✅ |

**结论**:数据简单、数量多、需要非技术人员维护 → YAML。
数据需要构造逻辑、依赖前置条件 → 写代码。

本工程两种都用:金额场景用 YAML,权限场景用代码(因为需要两个 token)。

## 5. 缺陷用例为什么用 marker 而不是 xfail?

被测系统是故意有缺陷的,所以"断言正确行为"的用例**必然失败**。

方案对比:

| 方案 | 效果 | 问题 |
|---|---|---|
| 直接跑,接受红灯 | 直观 | 默认套件永远红,CI 会挂 |
| `@pytest.mark.xfail(strict=True)` | 套件保持绿,修复后报 XPASS | 语义容易误解,报告不直观 |
| **独立 marker + 默认排除** | 默认绿;`-m bug` 主动查看 | 需要记住命令 |

选了第三种。原因:**红灯本身是教学材料**,`-m bug` 让你主动去面对它,而不是被它淹没在默认输出里。

CI 里只跑正常套件;缺陷追查是本地练习,不进流水线。

## 6. 报告选型:pytest-html vs Allure

| | pytest-html | Allure |
|---|---|---|
| 依赖 | 无 | 需要 Java |
| 产物 | 单文件 HTML | 静态资源目录 + 服务 |
| 易分享 | ✅ 双击即看 | 需要打包或起服务 |
| 历史趋势 | ❌ | ✅ |
| 步骤级详情 | 一般 | 强 |

**选 pytest-html**:工程需要的是"能直接发给别人看",而不是"长期质量看板"。
如果团队已经有 Allure 基础设施(Java + 报告服务),应该换 Allure。

**取舍要讲清楚**:不是 Allure 不好,是它在这个场景下成本高于收益。

## 7. CI 设计

```yaml
uv sync --frozen          # 按 uv.lock 安装,保证可复现
uv run uvicorn ... &      # 后台起被测服务
curl /api/health          # 轮询等待就绪,而不是 sleep 固定秒数
uv run pytest --junitxml  # 执行并产出机器可读结果
upload-artifact           # HTML 与 JUnit 都归档
```

**两个细节值得讲**:

1. **等待就绪用轮询,不用 `sleep 5`。** 固定睡眠在慢机器上会假失败,在快机器上浪费 5 秒。
2. **`uv sync --frozen`** 保证 CI 用的依赖版本和本地完全一致。不用 `--frozen` 的话,CI 可能解析出不同的版本,出现"本地过、CI 挂"。

## 8. 已知局限与演进方向

诚实地列出来,比假装完备更有说服力。

| 局限 | 影响 | 改进方向 |
|---|---|---|
| 被测服务是内存存储 | 无法测并发、持久化 | 接真实服务或加数据库 |
| 没有并发用例 | 测不出竞态条件 | 加 `pytest-xdist` + 并发下单用例 |
| 断言以等值为主 | 复杂业务规则表达力弱 | 引入假设检验 / 自定义 matcher |
| 没有性能基线 | 接口变慢发现不了 | 加 `elapsed_ms` 阈值断言 |
| 缺少失败重试机制 | 偶发失败会打断 CI | 加 `pytest-rerunfailures`,但需谨慎掩盖真问题 |
| 没有契约测试 | 上下游变更发现晚 | 引入 Pact 或 OpenAPI schema diff |

## 9. 面试可讲的三点

1. **分层不是为了好看,是为了让"变化"只影响一处。** 举例:接口路径改版时,改动从 N 个用例收敛到 1 个文件。
2. **断言的失败信息质量,直接决定排查效率。** 这是框架里最容易被忽略、收益最高的一环。
3. **测试隔离方案取决于被测系统的可干预程度。** 能重置就重置,不能就造唯一数据 —— 没有银弹,只有取舍。
